# Project Guidelines and Rules

Welcome to the OCT Insight Desktop development team. This document outlines the rules for navigating the codebase, writing code, and maintaining documentation. Adhering to these guidelines ensures cross-platform reliability, clinical safety, and long-term maintainability.

## 1. Codebase Navigation

The architecture strictly divides concerns into three pillars. Never bleed responsibilities across these boundaries:

- **`frontend/` (React/TS/Cornerstone)**: Exclusively for UI rendering, user interaction, and data visualization. 
  - *Rule*: Never perform heavy computations, data processing, or direct file I/O here.
  - *Entry point*: `frontend/src/App.tsx`
- **`tauri/` (Rust)**: Exclusively for OS-level interactions, process management, and IPC routing.
  - *Rule*: Never parse DICOM files or run machine learning models in Rust. Treat it merely as a highly performant bridge and window manager.
  - *Entry point*: `tauri/src/main.rs` & `tauri/src/lib.rs`
- **`python/` (Python/PyTorch)**: Exclusively for heavy lifting, ML model execution, and volumetric data parsing.
  - *Rule*: Never spawn UI windows or dialogs from Python. All outputs must be headlessly written to disk or sent to standard output (STDOUT/STDERR).
  - *Entry point*: `python/main.py`

## 2. Coding Standards

### TypeScript & React (Frontend)
- **Strict Typing**: Avoid `any`. Define strict interfaces for all models and API responses.
- **Styling**: Use Tailwind CSS utility classes exclusively. Avoid writing custom CSS unless absolutely necessary (e.g., specific Cornerstone canvas overrides).
- **Design Tokens**: Standard design tokens (colors, fonts) are defined as CSS variables in `index.css` via the Tailwind v4 `@theme` directive. Use variables like `var(--color-primary-accent)` or Tailwind utilities like `bg-primary-accent`.
- **State Management**: Keep state as close to where it's used as possible. For complex global states (like active study or linked viewer states), use React Context or a lightweight state manager like Zustand.

### Rust (Tauri Backend)
- **Idiomatic Error Handling**: Do not use `.unwrap()` or `.expect()` outside of initialization code. Use `Result<T, E>` and explicitly format error strings to be passed back to the frontend.
- **Asynchronous Execution**: Heavy I/O tasks must be pushed to `tauri::async_runtime::spawn` to avoid blocking the main thread.

### Python (Sidecar)
- **Modularity**: ML logic should be isolated from parsing logic.
- **Hardware Acceleration**: Always probe for `cuda` and `mps` (Apple Silicon) before falling back to `cpu`.
- **Dependency Management**: Ensure all new dependencies are pinned and documented via `uv` in `pyproject.toml`.

## 3. IPC & Data Transfer Philosophy

**"Zero-Lag IPC for Heavy Data"**
- Do **NOT** serialize massive 3D volumetric arrays (OCT scans) into JSON to pass between Python, Rust, and the frontend. 
- **Workflow**: Python processes the array -> Dumps binary `.raw` buffers to a temporary cache -> Tauri serves them via the custom `oct-asset://` protocol -> Frontend `CornerstoneJS` fetches and renders via the custom `octAsset` image loader pattern.

## 4. Documentation Rules

- **Documentation is Code**: If you change how a system works, you must update the documentation in the same Pull Request.
- **Markdown Standards**: Use standard GitHub-flavored Markdown. 
- **Inline Comments**: Use comments to explain *why* something is done (e.g., a specific WebGL hack), not *what* is being done. Code should be self-documenting.
- **Architecture Updates**: If introducing a new major component (e.g., a new local database), create a corresponding `.md` file in this `docs/` folder explaining its schema and lifecycle.

## 5. Clinical Safety & Logging

- **No PHI in Logs**: Never log Patient Health Information (PHI) to STDOUT or file logs.
- **Immutable Source Data**: Always treat the imported DICOM files as strictly read-only.
- **Clear AI Provenance**: Any UI element displaying data generated by the Python sidecar must be clearly labeled as "AI-Generated".
